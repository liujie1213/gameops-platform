# 游戏服务接入指南

## 在本机完成第一次联调

1. 打开运营后台，在「游戏接入」创建一款专门用于联调的游戏，复制一次性展示的游戏密钥。切换到这款游戏，在「聊天黑白库」添加黑库词条「代练接单」，使用「包含匹配」并启用。新游戏的行为策略默认为「仅观察」。首次接真实游戏时保持此模式，核对举报量和命中组。要在独立测试游戏中演示冻结回执，在「规则配置」将「命中后的动作」改为「执行处罚」，点击「发布规则」后再运行示例。
2. 保持平台服务运行，双击 gameops 目录的 `game-client.cmd`。也可以在安装了 Python 3 的终端进入 gameops 目录，执行 `python integration/simulate.py`。平台默认地址为 `http://127.0.0.1:8765`。如果使用其他地址，加上 `--url 地址`。粘贴密钥并回车，终端会隐藏输入。可在游戏服务进程环境中用 `GAMEOPS_GAME_TOKEN` 提供令牌。
3. 查看程序输出和后台数据。模拟器用 HTTP 上报 31 级玩家的等级、一条聊天和来自 15 个不同玩家的举报，再上报普通爆破、KD 为 2、击杀 20、对局玩家平均等级 20 的对局。按初始策略会命中第③组；若已改动策略，结果以已保存的版本为准。
4. 当平台发出冻结指令时，模拟器会将绝对到期时间写入独立的模拟账号库，读取该记录判断登录可用性，再上报执行回执。后台显示处置成功后，可以对照相同的玩家、对局和命令编号。退出后再运行会生成新对局。网络中断后用相同密钥重跑，模拟器从上一次未完成的演练恢复。

`gameops_client.py` 可复制到游戏服务端作为调用示例。`simulate.py` 是与平台独立的游戏进程；它的账号流水保存在 `integration/data/simulator.sqlite3`。模拟器仅处理本次生成的玩家、对局和对应命令。正式接入时，让游戏服的账号服务执行冻结，并让登录或游戏入口读取该状态。

## 请求与身份

根路径为 `/api/v1`。每款游戏使用自己的 `Authorization: Bearer <游戏密钥>`。POST 发送 UTF-8 JSON 对象，带 `Content-Type: application/json`。游戏身份由服务端从令牌确定；将密钥保存在游戏服务端。远程部署使用 HTTPS。密钥轮换后游戏服务需要切换到新密钥。

同目录下的 [openapi.json](./openapi.json) 是 OpenAPI 3.1 接口定义，包含六个游戏端接口的请求、响应、必填项、错误码和鉴权方式。可交给游戏团队导入支持 OpenAPI 3.1 的开发工具。切换到对应部署的服务地址，再填写测试游戏密钥。

所有 POST 事件带 `event_id` 字符串，在同一款游戏内跨事件类型保持唯一。调用方在首次投递前保存编号和请求体，遇到超时，重发完全相同的请求。可选 `occurred_at` 为 UTC Unix 秒整数，例如 10 位秒级时间戳。省略时使用平台接收时间。被重试的请求体继续使用原值，保持省略状态或原时间。客户端与平台服务器应校准时钟。

| 方法与路径 | 事件字段（除 event_id、occurred_at 外） | 游戏侧应处理的结果 |
| --- | --- | --- |
| POST /chat | player_id、text | decision 为 allow 或 block，hits 为命中黑库词条。整条消息与启用的白库条目完全相同时优先放行，hits 为空，allowed_by 返回该白库词条；其他消息的 allowed_by 为 null。发送前等待结果，在游戏服执行放行或拦截。 |
| POST /levels | player_id、level | accepted 表示已接收玩家等级。 |
| POST /reports | reporter_id、player_id（被举报人）、category（如 cheating） | accepted 表示已接收举报。策略按游戏独立设置计数口径。 |
| POST /matches | player_id、match_id、game_type、kd、kill_num、average_rank，可选 level | decision、hits（命中组号列表）、report_count、policy_version 和可能的 command_id。观察模式命中返回 observed，保留命中组，command_id 为空；执行模式命中返回 hit 并下发指令。 |
| GET /commands | 无请求体 | items 下为本游戏可执行命令，最多 100 条。每条包含 command_id、player_id、match_id、action、duration_seconds、created_at、expires_at。 |
| POST /receipts | command_id、status，选填 message | status 使用 succeeded 或 failed；返回命令编号和状态。 |

玩家、对局、举报人编号在游戏内保持稳定，作为字符串传输。游戏模式 2 与 5 对应普通爆破、排位爆破。kd 和 average_rank 为非负数，level、kill_num、game_type 为整数。average_rank 代表对局玩家平均等级。直接提交 level 时应填写结算当时的等级；选择使用等级上报时，先发送对应的等级记录，再发送对局结算。

### 计数与交付顺序

初始策略统计结算时间前 24 小时内该玩家被举报的事件数，可配置按独立举报人计数及举报类别。设结算时间为 T，统计范围为 (T−86400, T]。用于判定的举报、等级和结算信息应按业务顺序可靠投递。已经返回的结算结果保留当时的证据和策略版本，晚到举报不会回写该结果。提交结算的 game_type、KD 等数值由游戏服生成。对零死亡局使用哪种 KD 算法应由接入双方确认。

例如下面的请求使用此前上报的玩家等级：

~~~json
{"event_id":"match-402-p17-v1","match_id":"402","player_id":"p17","game_type":2,"kd":2,"kill_num":20,"average_rank":20}
~~~

### 处罚命令与重试

游戏服定期拉取待执行命令。领取不会删除命令；未到期且未提交回执的命令可能再次出现。以 command_id 作为游戏侧执行流水的唯一编号，将玩家状态变更和流水一起提交。同一编号重复到达时返回第一次的执行结果，使用 expires_at 作为绝对截止时间，以免重复请求延长冻结。成功回执须在游戏服确认执行后发送。执行失败可回传 failed 和一条运营人员能理解的原因。运营重试后，游戏服继续使用相同的命令编号；一次真正的重试结果使用新的回执 event_id。

~~~
GET /api/v1/commands
游戏服务执行 freeze，并保存 command_id 和 expires_at
POST /api/v1/receipts
{"event_id":"ack-402-p17-01","command_id":"使用实际返回的编号","status":"succeeded","message":"账号冻结已写入"}
~~~

在线游戏应为同步聊天接口设置与发言体验匹配的超时，并自行确定超时后的处置方式。举报、等级、对局和回执适合由游戏侧持久队列投递。网络中断或 5xx 可使用退避重试；如果服务返回 429，等待后再试。401 检查密钥及是否已轮换。400 检查字段和时间；匹配所需的玩家等级缺失时，可先补报等级，再重发结算。404 检查命令编号及所属游戏。409 表示编号与已有业务数据冲突，应核对原请求。每个玩家的每场对局只提交一次结算。
